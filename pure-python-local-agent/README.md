# AgenticGPT — Pure Python Agentic AI

A working AI agent built in **pure Python**, without LangChain, LangGraph, CrewAI, or AutoGen.

The goal is to understand how an agent works internally before reaching for a framework. Everything a framework hides — the tool schemas, the message list, the loop that decides when to stop — is written out here in plain Python.

**Version 2** replaces the hardcoded tool registry with **MCP (Model Context Protocol)**. The tools now live in their own server process and are discovered at run time instead of being imported. [Version 1](#version-1--direct-tool-calling) is still in the repo and still runs.

---

## What the agent does

- Understands a user request
- Discovers which tools are available from the MCP server
- Decides whether a tool is required
- Asks MCP to execute it
- Reads the result and continues, or answers

---

## Architecture

![AgenticGPT architecture](agenticgpt_architecture.svg)

The dashed boundary matters: Streamlit, the agent loop, and the MCP client all share one Python process. `server.py` is a **separate subprocess**, spawned over stdio, and the tools run inside it. The frontend never imports a tool function — it never even knows their names until the server reports them.

```text
Browser
   ↓  prompt
streamlit_app.py          renders chat, captures the agent's stdout trace
   ↓  asyncio.run()
run_agent()               the loop — up to 5 turns
   ↓  ⇅                   ⇅
Ollama (qwen3:8b)      MCP client  →  server.py subprocess  →  tools
```

## What version 2 changed

| | Version 1 | Version 2 |
|---|---|---|
| Tool wiring | `TOOLS_BY_NAME` dict in `tools.py` | discovered via `client.list_tools()` |
| Tool schemas | hand-written JSON | generated by FastMCP from type hints and docstrings |
| Execution | direct Python call | `await client.call_tool()` over stdio |
| Tool process | same process as the agent | separate subprocess |
| Backends | Ollama + Groq | Ollama (local only) |
| Calculator | raw `eval()` | AST walker, arithmetic only |

The practical payoff: adding a tool means writing one decorated function in `server.py`. No schema to write, no registry to update, no frontend change. The same server also works with any other MCP client, Claude Desktop included.

The cost: a fresh `python server.py` subprocess spawns on every message, and the tool schemas are re-sent to the model on every turn.

### `mcp_server/server.py`

Tools are plain functions with a decorator. FastMCP reads the signature and the docstring to build the schema the model sees, so the docstring is written for the model, not for a human reader.

```python
@mcp.tool
def convert_currency(amount: float, from_currency: str, to_currency: str) -> str:
    """Convert an amount between two currencies at today's rate.

    Uses the Frankfurter API. Currency codes are three letters, e.g. USD, INR.
    """
    ...
```

### `mcp_server/app.py`

`run_agent()` opens an MCP session, lists the tools, translates their schemas into Ollama's tool format, and runs the loop: send messages, execute whatever the model asks for, append the result, repeat until it answers without requesting a tool.

The client is built per call rather than once at import. Streamlit runs `asyncio.run()` on every message, which creates a new event loop each time, and an MCP client holds subprocess pipes bound to the loop that opened them — reusing one across loops works on the first message and fails on the second.

### `streamlit_app.py`

Chat UI, model picker driven by `ollama list`, and an **Agent trace** expander under every answer showing which tools were discovered, what arguments the model chose, and what came back.

## Tools

| Tool | Purpose | Network |
|---|---|---|
| `get_weather` | Current conditions for a city | WeatherAPI |
| `convert_currency` | Live exchange rates | Frankfurter |
| `search_internet` | Web search | Tavily |
| `calculator` | Arithmetic expressions | none |

`calculator` parses the expression and walks the AST, permitting only numbers and `+ - * / // % **`. The expression reaches it from the model, which is influenced by user input and — through `search_internet` — by web page content, so `eval()` on that path is arbitrary code execution.

## Installation

```bash
git clone https://github.com/akshatDE/AgenticAILearning.git
cd AgenticAILearning/pure-python-local-agent
pip install -r requirements.txt
```

Pull a model and start Ollama:

```bash
ollama pull qwen3:8b
ollama serve
```

Create a `.env` with your keys:

```text
WEATHER_API_KEY=your_weatherapi_key
TAVILY_API_KEY=your_tavily_key
```

Both are free tiers. The MCP server inherits these from the parent process when it's spawned, so nothing extra is needed to pass them through. `.env` is git-ignored.

## Running it

```bash
streamlit run streamlit_app.py
```

Or without the UI:

```bash
python mcp_server/app.py
```

The MCP server starts itself. There's no second terminal and no `python server.py` — the client spawns it.

## Worth knowing

**The tool schemas ride in the context window on every request.** Ollama is stateless per call, so each turn re-sends the full message list plus every tool definition. Four tools is roughly 400–700 tokens of overhead per turn. What actually grows is the history — one `search_internet` call can append a few thousand tokens that then travel with every later turn of the same question.

**The FastMCP banner appears once per message.** That's the subprocess booting. It goes to stderr, so it can't corrupt the JSON-RPC stream on stdout. Silence it with `mcp.run(show_banner=False)`.

**There is no system prompt.** The message list starts with the user turn. Ollama's chat template injects the tool definitions, but the model gets no instruction on when to use them or how to phrase an answer. Adding one is the cheapest quality win available here.

## Current limitations

- No conversation memory across turns — `run_agent()` starts from an empty message list each time
- A new server subprocess per message, so discovery re-runs every time
- Tool execution is synchronous and sequential
- Answers are streamed cosmetically; the model call itself is not streamed
- Cannot be hosted — Ollama has to run on the same machine

## Version 1 — direct tool calling

The original build, kept for comparison. No MCP: tools are Python functions in `tools.py`, their JSON schemas are written by hand, and a `TOOLS_BY_NAME` dict maps the name the model returns back to the function. The loop calls it directly, in-process.

It runs against **two backends** — Ollama locally, or Groq (`openai/gpt-oss-120b`) in the cloud — switchable from the sidebar. Groq exists because a 9B model can't be hosted on free infrastructure, which is what made a live demo possible: **[try it →](https://akshatde-agenticailearning-pure-python-local-agentapp-qgqnq1.streamlit.app/)**

Supporting both surfaced a detail a framework would have hidden: Ollama returns tool arguments as a **dict**, Groq as a **JSON string**; and Ollama accepts a `tool_name` key on tool results while Groq rejects it and requires `tool_call_id`. Worth seeing once.

```bash
python agent.py          # terminal
streamlit run app.py     # UI
```

Its known rough edges — raw `eval()` in the calculator, the WeatherAPI key hardcoded in source — are fixed in version 2.

## Core concepts

1. **Brain** — the model, deciding what to do
2. **Tools** — functions that act on the world
3. **Tool schemas** — how the model learns what exists (hand-written in v1, generated by MCP in v2)
4. **Memory** — the message list
5. **Agent loop** — choose → execute → observe → repeat

A chatbot is `question → answer`. An agent is `question → choose action → execute → observe → decide again → answer`. The model isn't only generating text; it's deciding what should happen next.
